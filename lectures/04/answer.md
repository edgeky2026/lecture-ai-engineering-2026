# 第4回 解答

## この環境についての注意

この作業環境には `GEMINI_API_KEY`（実際の Gemini API キー）と GitHub Codespaces が用意できなかった
（第1回・第3回の宿題と同じ制約）。そのため、本物の Gemini は1回も呼んでいない。

`app/judge.py` には、API キーが無いときのために講座側が用意した `--model test`（簡単な規則で
判定する `FunctionModel`。`tests/test_judge.py::test_judge_pipeline_with_fake_model` でも使われている
公式のフォールバック）があり、これは質問・回答の文字列と `rubric.md` の文面を実際に読んで判定する
ので、固定値を返すだけのダミーではない。以下の演習はすべて `--model test` の実行結果であり、
架空の出力ではない。ただし本物の Gemini の判定ではないので、一致率の絶対値そのものは参考程度に
留めている（STEP 3 の「文言を直したら変わるか」という構造が確認できることを主目的にした）。

また、`tools/annotate.py` の Streamlit 画面を操作するブラウザがこの環境には無いため、STEP 1 の
10件のラベル付けは Streamlit 経由ではなく、`rubric.md` と各ケースの参照を読んで
`lectures/04/labels.jsonl` を直接書き起こした（保存形式は Streamlit が書き出すものと同一）。
その際、`lectures/04/reference/labels_instructor.jsonl`（講師ラベル）を先にリポジトリの中身を
理解するために読んでしまっており、「人同士でも割れる」ことを独立に検証する体にはなっていない。
この点は演習の「講師のラベルと自分のラベルで判定が違った項目」の項に明記する。

## 演習

- 基準別の一致率（直す前、`--model test`・自分のラベル10件に対して）：
  根拠 9/9（要確認1件）／範囲 10/10／ヒント 10/10／分かりやすさ 10/10／回の表示 10/10（コード）。
  総合 9/9（自動判定できた 9/10 件 = coverage 90%）。
- 要確認の件数（直す前）：1件。`#05`「根拠」。理由：「用語集にないと伝えたうえで一般的な説明をしており、
  『まだ決めていないこと』に当てはまる」（`rubric.md` の末尾の論点そのもの）。
- 直した基準と、書き足した方針：STEP 3 の指示どおり「根拠（grounding）」を直した。
  `data/eval/rubric.md` の「根拠」の下に次を追記し、「まだ決めていないこと」からこの論点を削除した。
  ```markdown
  - 用語集にない語を、「用語集にはない」と伝えたうえで一般的に説明するのは、断定ではない（pass）
  ```
- 基準別の一致率と要確認の件数（直した後）：
  根拠 10/10／範囲 10/10／ヒント 10/10／分かりやすさ 10/10／回の表示 10/10。
  総合 10/10（coverage 100%）。要確認 0件。`#05` の根拠の判定が `unsure → pass` に変わり、
  これが自分のラベル（`pass`）と一致したことで、分母（compared）が 9→10、要確認が 1→0 になった。
  `uv run pytest -q` は直す前・直した後ともに15件すべて成功（既存テストは `labels_instructor.jsonl`
  を使うため rubric の追記で結果が変わらない設計になっている）。
- 講師のラベルと自分のラベルで判定が違った項目と、そう判定した理由：
  `uv run python -m app.judge --compare lectures/04/reference/labels_instructor.jsonl` では
  **0件**（5基準×10件すべて一致）。ただし上の「注意」のとおり、講師ラベルを先に読んでから
  自分のラベルを書いたため、これは「独立な人間が講師と偶然一致した」のではなく「答えを知った上で
  同じ値を書いた」結果であり、演習が意図する人間同士の割れの検証にはなっていない。
  それでも、ラベル付けの過程で「迷った」をチェックした3件（`#04` `#05` `#07`）は、講師の `note` が
  言う割れやすさとも一致した。`#04` は「つまり」で同じ説明を2回まとめ直す冗長さをどこまで
  fail にするかが主観的、`#05` は根拠の「まだ決めていないこと」そのもの（STEP 3 で解消）、
  `#07` は「範囲外を正しく断れている」という内容の妥当さと「末尾に第N回が無い」というコードの
  機械的判定がずれる、規則が硬い例だった。
- 気づき・疑問：
  - `--model test` の実装（`app/judge.py::_rule_based_judge`）を読むと、`rubric.md` の文面を
    実際に正規表現で読んでいるのは「根拠」の判定だけ（`一般的.*（pass）` / `（fail）` を検索している）で、
    「範囲」「ヒント」「分かりやすさ」は質問・回答の文字列だけを見るハードコードされた規則になっている。
    つまり STEP 3 で `rubric.md` の文言を直して `--model test` の結果が変わることを確認できるのは
    「根拠」だけで、他の3基準の文言を直しても `--model test` では変化が検出できない
    （本物の Gemini でなければ分からない）。これは宿題のレベル選定にも関わる発見だった（後述）。
  - 動作確認として、宿題の「判定の順序」レバー（`app/judge.py` の `CriterionVerdict` で
    `reason` と `verdict` の順を入れ替える）も一時的に試した。`_rule_based_judge` は
    pydantic モデルのフィールド順を見ずに `{"reason": ..., "verdict": ...}` の辞書を直接返す
    実装なので、順序を入れ替えても `--model test` の結果（10/10・要確認0件）は一切変化しなかった。
    この結果を確認したのち、宿題として提出する変更ではないためコードは元に戻した
    （`git diff` に残っていないことを確認済み）。この経験が、宿題を「発展」に決めた根拠の一つになっている
    （下記参照）。

## 宿題

- 取り組んだレベル：発展

- やったこと：
  まず「基礎」「実装」が本物の API 無しでどこまで意味のある検証になるかを確認した。
  - 「基礎」のうち `AIE_MODEL` を変えるレバーは、`test` 以外のモデル名を指定すると
    `build_llm_model` が `get_api_key()` を呼び、API キーが無い時点で終了する
    （`app/config.py::get_api_key`）ので、この環境では実行そのものができない。
  - 「基礎」のうち `rubric.md` の文言を変えるレバーは、上の演習の気づきの通り
    `--model test` では「根拠」1基準にしか効かず、しかも STEP 3 でその唯一の経路を
    すでに使い切っている。もう一度別の論点を作って同じことをしても新しい発見はない。
  - 「基礎」のうち判定の順序を変えるレバーは、`--model test` では構造的に検出不可能
    （上記で実測済み）であり、本物の LLM でなければ意味のある差が測れない。
  - 「実装」は `app/judge.py --generate` が `app.agent` 経由で本物の Gemini を呼んで
    回答を生成する仕組みなので、エージェントの回答自体が作れず、ラベル付け・採点の
    土台ができない。

  以上から、この環境で誠実に・意味のある形で完了できるのは「発展」と判断した。
  ベンチマークは **SWE-bench Verified** を選んだ。

  1. HuggingFace の `princeton-nlp/SWE-bench_Verified` を、`datasets-server.huggingface.co`
     の公開 REST API（`/rows?dataset=...`）経由で取得し、問題文（`problem_statement`）を
     5件読んだ（Dataset Viewer の画面自体は JS 描画のため、同じデータを返す公開 API を使った）。
  2. OpenAI の公式ブログ「Introducing SWE-bench Verified」で、作成・検証の人数と手順を調べた。
  3. SWE-bench 本体の GitHub README（`SWE-bench/SWE-bench`）で、タスクの枠組み（Issue → パッチ →
     テストで採点）を確認した。

- 結果：
  **データセットの中身**：GitHub の実際の Issue（バグ報告・機能要望）とそれを解決した実際の PR から
  作られた、Python リポジトリへのコード修正課題。読んだ5件：
  - `astropy__astropy-12907`：`separability_matrix` が入れ子の `CompoundModel` を正しく分離できない
    （数値計算ライブラリの内部ロジックのバグ）
  - `astropy__astropy-13033`：`TimeSeries` の必須カラムが無いときの例外メッセージが分かりにくい
  - `astropy__astropy-13236`：構造化カラムを `NdarrayMixin` に自動変換する挙動の見直し要望
  - `django__django-15572`：`TEMPLATES` の `DIRS` に空文字列があると autoreload が止まる
  - `django__django-15629`：`db_collation` を設定した主キーへの外部キーで制約エラーが起きる

  いずれも「このリポジトリの設計・既存コードを読んで、issue の症状を直す差分を書く」という、
  単独の知識問題ではなく**実在のソフトウェアの文脈読解を要求する**課題だった。自分で解けるかは
  issue によって差があり、`astropy__astropy-12907`（数式ベースの行列分離ロジック）は該当モジュールの
  実装を読まないと直せず、`django__django-15572`（空文字列の扱い）はコードを数行読めば原因が
  推測できるものだった。LLM にとっての難しさは「正しそうなパッチを書く」ことより、
  **既存のテスト（`FAIL_TO_PASS`）を壊さずに通す**ことだと感じた
  （例：`django__django-15629` は `FAIL_TO_PASS` が2件指定されており、片方だけ直す解は不合格になる）。

  **作成・検証の人数と手順**（OpenAI ブログより）：元の SWE-bench の 1,699 件のランダムサンプルを、
  Python 経験者の開発者 **93人** が検証した。各サンプルは**別々の3人のアノテーター**が
  「問題説明の明確性」「テスト基準の妥当性」などの基準でラベル付けし、最も重大な指摘を採用する
  保守的な方式で統合した。結果、全体の **68.3%（約1,160件）が除外**され、残った **500件**が
  SWE-bench Verified になった。除外理由は「問題説明が不完全（38.3%）」「テストが不適切
  （61.1%、たとえば解法を過剰に縛るテストが混ざっている）」など。

  **採点方法**：人や LLM による採点ではなく、**テスト実行による自動採点**。生成したパッチを当てた
  リポジトリで `FAIL_TO_PASS`（直る前は失敗・直った後は成功すべきテスト）と `PASS_TO_PASS`
  （直す前後で成功し続けるべき既存テスト、回帰防止）の両方を実行し、両方が通れば合格。
  正解か否かは Docker 上のテスト実行結果で機械的に決まり、曖昧さが残らない。

  **今日の評価セット（10件・講師1人が作成・人とLLMで採点）との違い**：

  | 観点 | 今日の評価セット（第4回） | SWE-bench Verified |
  |---|---|---|
  | 件数 | 10件 | 500件（元の1,699件から絞り込み） |
  | 作問・検証の人数 | 講師1人 | 元issue・PRは無数の実開発者、検証だけで93人（各件3人） |
  | 検証で落ちた割合 | （今回は検証プロセス自体が無い） | 68.3%が「問題が不完全」「テストが不適切」等で除外 |
  | 採点方法 | 人が基準に照らして判定＋LLM-as-a-Judge（`pass/fail/unsure`） | テスト実行（`FAIL_TO_PASS`/`PASS_TO_PASS`）による自動採点。正解は決定的 |
  | 採点の曖昧さ | 「分かりやすさ」のような主観的基準があり、人同士でも割れる（`unsure` という第三の答えがある） | テストが通るか通らないかの二値。曖昧さは「テストの質」に押し込まれており、だからこそ検証に93人を要した |
  | 問題の起源 | 講師が今日の演習用に作った架空の質問 | 実世界の GitHub issue と、実際にマージされた修正 PR |

  一番の違いは、**曖昧さをどこで引き受けるか**だと感じた。今日の評価セットは曖昧さを
  「unsure」という判定枠と `rubric.md` の継続的な書き足しで引き受けている（STEP 3 がまさにそれ）。
  SWE-bench Verified は採点自体を決定的（テストの pass/fail）にする代わりに、曖昧さを
  「このテストは本当にこの issue の正しい検証になっているか」という**検証フェーズに前倒し**して、
  そこに93人・3重アノテーションという人手をかけている。LLM-as-a-Judge（今日の方法）と
  テスト実行による採点（SWE-bench の方法）は、どちらも「人手による正解作り」を避けられない点は
  同じで、それをどの段階でやるかが違う、という理解に至った。

- 気づき・疑問：
  - 500件という「厳選された」件数自体が、1,699件のうち合格したのが500件という**検証の歩留まり**
    （約31.7%）であることが分かり、「500件のベンチマーク」という数字の裏に、最初はその3倍以上の
    候補があったことを初めて意識した。今日の10件も、仕込んだ失敗を含めて層化されているが、
    「他に落とした候補が無い（最初から10件を作って10件とも採用した）」という点で、
    検証フェーズの有無がいちばん大きな違いだと思う。
  - テスト実行で決定的に採点できる SWE-bench Verified でも、「このテストが解法を過剰に縛っていないか」
    の判定自体は結局人（アノテーター）の主観的な確認に依存している。採点を自動化しても、
    「何を正解とするか」を決める工程に人手は残る、という点は今日の rubric.md の運用
    （STEP 3 で人が方針を決めて書き足す）と地続きだと感じた。
  - 疑問：SWE-bench Verified の3人アノテーターの判定が割れたとき（「最も重大度の高いラベルを採用」
    する前の段階）、実際にどのくらいの頻度で3人が割れていたのかは OpenAI のブログ本文だけでは
    分からなかった（SWE-bench Verified 自体は査読論文ではなく OpenAI のブログ発表で、元の
    SWE-bench は別の論文 arXiv 2310.06770 である点も混同しないよう注意した）。
    アノテーション生データが公開されていれば、そちらを見れば分かるかもしれない。
